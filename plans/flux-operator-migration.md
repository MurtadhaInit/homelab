# Flux Operator Migration

Replace the current `flux bootstrap`-managed Flux installation with the
controlplane Flux Operator, bootstrapped declaratively from OpenTofu using the
official `flux-operator-bootstrap` module. Seed the SOPS age key as part of
the same module run (Option B), drop the now-unused GitHub deploy key + token
flow, and follow up with state encryption once the new flow is verified.

## Rationale

The current bootstrap is the canonical `flux bootstrap github` flow: it works,
but the cluster's lifecycle is split across two orchestrators with a manual
handoff (tofu → justfile → flux-bootstrap), Flux upgrades require re-running
bootstrap by hand, and the generated `gotk-components.yaml` / `gotk-sync.yaml`
sit in git as inert artifacts that have to be hand-reconciled with reality on
every Flux release.

The Flux Operator replaces all of that with a single CRD (`FluxInstance`) that
declares the desired Flux installation; a small operator reconciles it. The
official Terraform module solves the bootstrap-ownership problem cleanly: an
ephemeral in-cluster Job applies the operator chart and the `FluxInstance`
server-side, so tofu doesn't need `kubernetes_manifest` and there's no
CRD-at-plan-time foot-gun.

End state, in one command after `seed-cluster-secrets` is gone:

```
tofu apply  →  Proxmox VMs → Talos cluster → Cilium → Flux Operator → FluxInstance
              + sops-age Secret (passed through the same module)
              → Flux reconciles k8s/clusters/homelab
```

## Goals

1. Replace `flux bootstrap` with the `flux-operator-bootstrap` Terraform module.
2. Drop the GitHub SSH deploy key and the `GITHUB_USER` / `GITHUB_TOKEN` env
   vars — the repo is public, so Flux needs no Git auth at all.
3. Seed the SOPS age key through the module's `managed_resources.secrets_yaml`
   so the bootstrap is single-command (Option B from the discussion).
4. Remove the now-stale `flux-bootstrap` and `seed-sops-secret` justfile
   recipes; remove the generated `gotk-*.yaml` files from the repo.
5. Encrypt OpenTofu state at rest via the native `encryption {}` block once the
   new flow is verified end-to-end.

Non-goals: changing the Flux components installed (still source / kustomize /
helm / notification — no image-automation), changing the directory layout
under `k8s/`, or adopting any commercial controlplane features.

## Public Repo Implications (the auth question)

The repo `MurtadhaInit/homelab` is public. That changes two things:

1. **Flux needs no Git auth.** Switch `sync.url` from
   `ssh://git@github.com/MurtadhaInit/homelab` to
   `https://github.com/MurtadhaInit/homelab.git` and omit `pullSecret` on the
   `FluxInstance.sync` spec. GitHub doesn't rate-limit anonymous git clones at
   any volume that matters for a 1-minute-poll homelab.

2. **The `GITHUB_USER` / `GITHUB_TOKEN` env vars in `.env` are
   bootstrap-only.** They were consumed by `flux bootstrap github` to create
   a deploy key on the user's behalf via the GitHub API. After this migration
   they are unused — Flux Operator never touches GitHub's API. Remove them
   from `.env` (and from `mise.toml` if exported there).

**Does Flux ever change the repo?** No. With the components selected in this
plan (source / kustomize / helm / notification), Flux is read-only on the Git
side — it pulls and reconciles, nothing more. Image-automation-controller
*would* push commits, but that's not installed and isn't in scope.

The single historical case where bootstrap *did* write to the repo was
`flux bootstrap github` itself, which committed `gotk-*.yaml` once. Eliminating
that flow eliminates the only writer.

## Architecture: Before → After

**Before**

```
tofu apply ─→ VMs / Talos / Cilium / kubeconfig
                                                          (manual handoff)
just seed-sops-secret ─→ kubectl create secret sops-age
just flux-bootstrap   ─→ flux bootstrap github → gotk files → SSH GitRepository
                                                          (Flux reconciles)
```

**After**

```
tofu apply ─→ VMs / Talos / Cilium / kubeconfig
              + flux_operator_bootstrap module
                  ├─ Helm: flux-operator chart
                  ├─ FluxInstance CR (HTTPS sync, no pullSecret)
                  └─ managed_resources: sops-age Secret
                                                          (Flux reconciles)
```

`flux-instance.yaml` is committed to `k8s/clusters/homelab/flux-system/` and
referenced by the module via `file()`, so the FluxInstance lives in git and
the operator self-reconciles it post-bootstrap (closing the GitOps loop on
Flux's own configuration).

## Plan

### 1. Add tofu providers and the bootstrap module

`Terraform-OpenTofu/versions.tf` — add the kubernetes provider; the helm
provider is already there.

```hcl
terraform {
  required_providers {
    # ... existing entries ...
    kubernetes = {
      source  = "hashicorp/kubernetes"
      version = "~> 2.30"
    }
  }
}
```

`Terraform-OpenTofu/providers.tf` — same lazy-config pattern as the existing
helm provider:

```hcl
provider "kubernetes" {
  config_path = "${path.module}/../k8s/kubeconfig"
}
```

`Terraform-OpenTofu/flux.tf` (new file):

```hcl
# === Flux Operator bootstrap ===
# Installs flux-operator and applies the FluxInstance via an ephemeral Job.
# Once Flux is up it self-reconciles flux-instance.yaml from the repo, so
# the operator and FluxInstance are GitOps-managed end-to-end.
#
# Re-bootstrap by bumping `flux_bootstrap_revision` (forces the Job to re-run).
module "flux_operator_bootstrap" {
  source  = "controlplaneio-fluxcd/flux-operator-bootstrap/kubernetes"
  version = "0.5.0"

  revision = var.flux_bootstrap_revision

  gitops_resources = {
    instance_yaml = file("${path.module}/../k8s/clusters/homelab/flux-system/flux-instance.yaml")
  }

  managed_resources = {
    # SOPS age key for decrypting *.sops.yaml files in the repo. The module's
    # bootstrap Job applies this Secret server-side; nothing here lands in git.
    # The key value is read from disk at apply time and ends up in tofu state —
    # acceptable because we encrypt state in step 7.
    secrets_yaml = templatefile("${path.module}/flux-secrets.yaml.tftpl", {
      sops_age_key = file(pathexpand(var.sops_age_key_path))
    })
  }

  depends_on = [
    helm_release.cilium,           # cluster networking must be up
    local_sensitive_file.kubeconfig,
  ]
}
```

`Terraform-OpenTofu/variables.tf` — add two variables:

```hcl
# === Flux ===
variable "flux_bootstrap_revision" {
  type        = string
  description = "Bump to force the Flux Operator bootstrap Job to re-run (idempotent re-apply)."
  default     = "v1"
}

variable "sops_age_key_path" {
  type        = string
  description = "Path to the SOPS age private key file. Seeded into the cluster as Secret/sops-age in flux-system."
  default     = "~/.ssh/keys/sops-age.txt"
  sensitive   = true
}
```

`Terraform-OpenTofu/flux-secrets.yaml.tftpl` (new file):

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: sops-age
  namespace: flux-system
type: Opaque
stringData:
  sops-age.agekey: |
${indent(4, sops_age_key)}
```

The `${indent(4, ...)}` pattern preserves multi-line key formatting — the age
key is single-line, but defensive indenting costs nothing.

### 2. Author the FluxInstance manifest

`k8s/clusters/homelab/flux-system/flux-instance.yaml` (new file, replaces
`gotk-components.yaml` + `gotk-sync.yaml`):

```yaml
apiVersion: fluxcd.controlplane.io/v1
kind: FluxInstance
metadata:
  name: flux
  namespace: flux-system
  annotations:
    fluxcd.controlplane.io/reconcileEvery: "1h"
spec:
  distribution:
    # Auto-upgrade within 2.x; bump to "2.7.x" or similar to pin tighter.
    version: "2.x"
    registry: "ghcr.io/fluxcd"
  components:
    - source-controller
    - kustomize-controller
    - helm-controller
    - notification-controller
  cluster:
    type: kubernetes
    size: small        # tune if Flux ever runs hot — homelab scale = small
    multitenant: false
    networkPolicy: true
  sync:
    kind: GitRepository
    url: "https://github.com/MurtadhaInit/homelab.git"
    ref: "refs/heads/main"
    path: "k8s/clusters/homelab"
    interval: "1m"
    # No pullSecret — public repo, anonymous HTTPS clone.
```

Update `k8s/clusters/homelab/flux-system/kustomization.yaml`:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - flux-instance.yaml
```

(The `gotk-*.yaml` references are removed — those files will be deleted in
step 5.)

### 3. Migration cutover sequence

This is the only step with ordering hazards. The current cluster has a
`Kustomization/flux-system` with `prune: true` reconciling
`./k8s/clusters/homelab`. If we push a commit removing `gotk-sync.yaml`
without first stopping that Kustomization, it will prune *itself* — breaking
the cluster mid-migration.

**Step 3a — verify cluster is healthy before touching anything.**

```nu
flux check
flux get all -A | rg -v "True\s+Ready"   # should be empty
```

**Step 3b — suspend the existing flux-system Kustomization.**

```nu
flux suspend kustomization flux-system -n flux-system
```

This stops the self-pruning loop. All other Kustomizations and HelmReleases
keep reconciling normally — only the meta-Kustomization that manages
`flux-system/` itself is paused.

**Step 3c — commit the new repo state.**

In a single commit on `main`:

- Add `k8s/clusters/homelab/flux-system/flux-instance.yaml`
- Update `k8s/clusters/homelab/flux-system/kustomization.yaml` to reference
  only `flux-instance.yaml`
- Delete `k8s/clusters/homelab/flux-system/gotk-components.yaml`
- Delete `k8s/clusters/homelab/flux-system/gotk-sync.yaml`
- Add `Terraform-OpenTofu/flux.tf`
- Update `versions.tf`, `providers.tf`, `variables.tf`
- Add `flux-secrets.yaml.tftpl`
- Update `justfile` (remove `seed-sops-secret`, `flux-bootstrap`)

Push.

**Step 3d — apply the bootstrap.**

```nu
just deploy-apply   # runs `tofu apply` in Terraform-OpenTofu/
```

What happens, in order:

1. The kubernetes/helm providers connect to the cluster (kubeconfig is on disk
   from the prior apply).
2. The `flux_operator_bootstrap` module spins up a Job in
   `flux-operator-bootstrap` namespace.
3. The Job installs the `flux-operator` Helm chart (idempotent — recovers if a
   previous install was stuck).
4. The Job applies the `sops-age` Secret to `flux-system` (already exists from
   the previous bootstrap; SSA reconciles it without changing the value
   because it's identical).
5. The Job applies the `FluxInstance` CR.
6. The flux-operator controller reconciles the `FluxInstance` and creates a
   `GitRepository` and `Kustomization` named `flux-system` in `flux-system`,
   server-side-applied with the operator as field manager. These overwrite
   the existing (suspended) GitRepository / Kustomization, including resetting
   the suspend status.
7. The new Kustomization syncs `./k8s/clusters/homelab` — same path, same git
   contents minus the gotk files. All in-cluster resources continue
   reconciling.

The Job exits when the FluxInstance is `Ready`. tofu state records the
completed bootstrap; the operator and FluxInstance are then steady-state.

**Step 3e — verify.**

```nu
flux check
flux get sources git -A
flux get kustomizations -A
flux get helmreleases -A
kubectl get fluxinstance -n flux-system flux -o yaml | rg "ready:|message:"
```

All should be `Ready=True`. The GitRepository should now show the HTTPS URL
and no `secretRef`.

### 4. Remove the deploy-key Secret and stale flux artifacts

The old SSH deploy-key Secret is now orphaned — nothing references it.

```nu
kubectl delete secret -n flux-system flux-system
```

(That's the literal name `flux-system` for the Secret in the `flux-system`
namespace; bootstrap created it.)

Also clean up the deploy key from GitHub: Settings → Deploy keys → delete the
"flux" entry. And delete the matching local file if it exists
(`~/.ssh/keys/flux-deploy*` — verify before deleting; might not exist if the
bootstrap was done without a separate file).

### 5. Justfile and `.env` cleanup

Remove from `justfile`:

```just
# 1. Supply the Age private key to the cluster ...
seed-sops-secret: ...

# 2. Bootstrap the cluster with Flux ...
flux-bootstrap: ...
```

Remove from `.env` (or wherever `mise` reads them):

```
GITHUB_USER=...
GITHUB_TOKEN=...
```

Both were only consumed by `flux bootstrap github`. Confirm with a repo-wide
grep before deletion.

### 6. Update README / docs

The README's bootstrap section currently walks the user through
`generate-keys → copy-keys → pve-hosts → deploy-apply → seed-sops-secret →
flux-bootstrap → pve-postconfig`. Collapse the middle three steps:

```
just generate-keys
just copy-keys
just pve-hosts
just deploy-apply       # now also installs Flux Operator + FluxInstance
just pve-postconfig
```

Note in the bootstrap section that `~/.ssh/keys/sops-age.txt` must exist
before `deploy-apply` (the file is read at plan time).

### 7. Encrypt tofu state — separate phase, after step 6 is verified

OpenTofu 1.7+ supports native state encryption via the `encryption {}` block.
The flow:

**Step 7a — choose a key source.** For a local-state homelab the simplest is a
PBKDF2-derived key from a passphrase stored in `mise`'s secret env. Better:
use OpenBao / Vault / 1Password CLI to inject the key. Pick one that fits the
existing tooling — `mise` is already the env-var hub here.

**Step 7b — add the encryption block** to `Terraform-OpenTofu/versions.tf`:

```hcl
terraform {
  encryption {
    method "aes_gcm" "default" {
      keys = key_provider.pbkdf2.passphrase.keys
    }
    key_provider "pbkdf2" "passphrase" {
      passphrase = env("TOFU_STATE_PASSPHRASE")
    }
    state {
      method   = method.aes_gcm.default
      enforced = true
    }
    plan {
      method   = method.aes_gcm.default
      enforced = true
    }
  }
}
```

**Step 7c — migrate existing state** by running `tofu apply` once with both
the old and new method blocks (using `fallback {}` for the unencrypted-input
case). See OpenTofu docs: state encryption migration. The first apply rewrites
`terraform.tfstate` in encrypted form.

**Step 7d — verify** by removing the fallback and re-running `tofu plan` — it
should still work with the passphrase set, and fail cleanly without it.

**Critical**: do not skip step 7. The SOPS age key now lives in tofu state;
plaintext state on disk is a backwards step from the prior setup where it
only lived in `~/.ssh/keys/`.

## Edge Cases

### A. The bootstrap Job fails halfway

Symptoms: `tofu apply` errors out citing a Job failure; `kubectl logs -n
flux-operator-bootstrap job/...` shows the actual reason.

The module is designed for this: re-running `tofu apply` re-runs the Job
(idempotent). If genuinely stuck, set `debug_on_failure = true` on the
module — the Job pauses on failure for inspection. Bump
`flux_bootstrap_revision` to force a clean re-run after fixing the cause.

### B. Operator-managed GitRepository / Kustomization name collision

The operator creates resources named `flux-system` by default — the same
names the bootstrap created. The cutover in step 3 relies on server-side
apply overwriting them.

If the existing resources have field-manager annotations that conflict (e.g.
`fluxcd.io/managed-by` set to something the operator refuses to overwrite),
the FluxInstance will be `Reconciling` indefinitely with a clear error.
Resolution: `kubectl delete gitrepository -n flux-system flux-system` and
`kubectl delete kustomization -n flux-system flux-system` *while the
Kustomization is suspended* (so the deletion doesn't trigger a prune
cascade), then let the operator recreate them.

### C. Self-prune cascade if step 3b is skipped

If you push the commit removing `gotk-sync.yaml` *before* suspending, the
existing Kustomization will reconcile, see the missing inventory entries, and
attempt to prune the `GitRepository` and `Kustomization` named `flux-system`
— deleting itself mid-deletion. The cluster's other Kustomizations keep
reconciling (they're independent), but Flux is now headless until manually
recreated.

Recovery: re-run `flux bootstrap github ...` from the previous-state branch,
or skip directly to applying the new tofu module (the operator will
self-heal). Suspending in step 3b avoids this entirely.

### D. SOPS age key path doesn't exist at plan time

`file(pathexpand(var.sops_age_key_path))` errors at plan time, not apply.
Symptom: `tofu plan` fails with "no such file" before any apply happens.
Resolution: ensure `~/.ssh/keys/sops-age.txt` exists, or override
`-var sops_age_key_path=...`.

This is a feature, not a bug — failing fast at plan time prevents a
half-bootstrapped cluster.

### E. The kubernetes provider panics if kubeconfig is absent on first plan

On a *truly fresh* `tofu apply` against an empty state, neither the kubeconfig
file nor the cluster exists yet. The kubernetes/helm providers configure
lazily, so this works as long as nothing the providers manage is *read* at
plan time. The `flux_operator_bootstrap` module passes the FluxInstance YAML
as a string (not via a kubernetes resource), so plan-time evaluation is safe.

If a plan-time error does surface, it's almost certainly the `file()` call
on `instance_yaml` — but that file is in-repo and always present, so this
shouldn't happen.

### F. `flux-system` Secret deletion (step 4) before SSH GitRepository is gone

Don't run step 4 until step 3e verifies the new GitRepository is HTTPS-mode
and `Ready`. If you delete the deploy-key Secret while the old SSH
GitRepository is still active, source-controller will start failing auth and
all downstream reconciliations will halt. The verification in 3e is the gate.

### G. Cluster rebuild (future)

After this plan lands, rebuilding from scratch is:

```nu
just generate-keys     # (regenerates sops-age key — write down the recovery seed)
just copy-keys
just pve-hosts
just deploy-apply
just pve-postconfig
```

Note: regenerating the SOPS age key means existing `*.sops.yaml` files in the
repo are no longer decryptable. For a true "rebuild and restore" you must
preserve `~/.ssh/keys/sops-age.txt` from the previous cluster (or have it in
a password manager / backup). This is not new — the same is true today.

### H. OpenTofu version

Native state encryption requires OpenTofu **≥ 1.7**. Verify with `tofu
version` before step 7. The `mise` config probably already pins a recent
version; confirm.

### I. Helm provider major-version compatibility

The bootstrap module was published against a specific helm provider major.
Pinned `hashicorp/helm 3.1.1` here is current (3.x line). If the module
documents a different range, pin accordingly — check
`registry.terraform.io/modules/controlplaneio-fluxcd/flux-operator-bootstrap/kubernetes`
for the provider requirements at install time.

## Order of Operations

1. **Read this plan end-to-end and skim the operator's own migration doc** at
   `docs/guides/operator/operator-migration.md` in the flux-operator repo to
   confirm nothing has changed since 0.5.0.
2. **Pre-flight**: cluster healthy (`flux check`), `~/.ssh/keys/sops-age.txt`
   present, OpenTofu ≥ 1.7.
3. **Branch + commit** the changes from steps 1–2 (tofu files + flux-instance
   + kustomization.yaml update + gotk file deletions + justfile cleanup).
4. **Suspend** the existing `flux-system` Kustomization (step 3b).
5. **Push and merge** the branch.
6. **`tofu apply`** — installs operator, applies FluxInstance, seeds sops-age.
7. **Verify** (step 3e). If broken, see edge cases A–C.
8. **Cleanup** the deploy-key Secret + GitHub deploy key + env vars.
9. **Update the README**.
10. **State encryption** (phase 7) — separate PR.

## Open Questions / Verifications Needed

- **Module v0.5.0 helm provider range**: check the module's `versions.tf` on
  the registry for the actual `helm` and `kubernetes` provider constraints
  before pinning. If the module wants `helm ~> 2.x` we'll need to pin
  accordingly (the existing Cilium release was authored against `helm 3.x` so
  a downgrade is awkward — flag for handling if it comes up).
- **Operator chart version pinning**: the module installs whatever the latest
  flux-operator chart is unless overridden. Decide whether to pin
  `gitops_resources.operator_chart.version` or float on `latest`. For a
  homelab "explicitly current" beats "auto-upgraded silently" — pin and bump
  via PR.
- **`FluxInstance.spec.cluster.size`**: `small` is a guess based on Flux's
  documented presets. Once the cluster is up under load (kube-prometheus-stack
  scraping all the things), watch `kubectl top pods -n flux-system` and bump
  to `medium` if anything is throttled or OOMing.
- **`reconcileEvery` annotation**: 1h is the operator's default for
  reconciling the FluxInstance itself — separate from `sync.interval` (1m)
  which controls how often Flux pulls git. Both are sensible; flagged so the
  distinction is on the record.
- **Capacitor UI install**: out of scope for this plan but ready to add as a
  HelmRelease once the operator-managed Flux is verified — see prior
  discussion. Not gated on this work.
